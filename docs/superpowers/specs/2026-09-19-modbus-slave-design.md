# STM32F103C8T6 Modbus RTU 从机改造设计

日期：2026-09-19
状态：待评审

## 背景

现有工程 `d:\32 Project\Modbus2.0` 把 STM32F103C8T6 实现为 Modbus RTU **主机**：

- 每 2 秒通过 RS485 发出请求帧 `{0x01,0x04,0x00,0x00,0x00,0x02,0x71,0xCB}`（读从机 1 的输入寄存器 0x0000~0x0001）
- 串口中断逐字节收，TIM2 1ms 中断做 5ms 空闲超时判帧尾
- `jiema.c` 解析应答帧，取温度、湿度显示到 OLED

本次改造把这个工程变成 Modbus RTU **从机**，用于和另一块跑现有主机代码的 STM32 对测。

## 目标与非目标

**目标**

1. 从机地址 0x01，响应 0x03 / 0x04 / 0x06 / 0x10 四个功能码
2. 模拟原温湿度传感器：寄存器 0x0000 = 温度、0x0001 = 湿度，编码方式与原传感器一致，使现有主机代码**一行不用改**就能读通
3. 寄存器值可被主机通过 0x06 / 0x10 写入，写入后立即生效

**非目标**

- 不做线圈 / 离散量（0x01 / 0x05 / 0x0F）
- 不做 ASCII 传输模式
- 不做波特率 / 校验位在线修改（改了要重配 USART，本次不需要）
- 不保留主机功能（主机代码在 git 提交 `3c93c22` 中完整存在）

## 关键设计决策

### 决策 1：0x03 与 0x04 共用同一片寄存器区

一个 `uint16_t Modbus_Reg[64]` 数组，0x03 和 0x04 都读它，0x06 和 0x10 都写它。

理由：现有主机用 0x04 读温湿度，若把温湿度放进只读的"输入寄存器"区、另外维护一套可写的"保持寄存器"区，代码量翻倍而本次用不到。共用一片后，上位机（Modbus Poll 等）用 0x03 或 0x04 都能读通，调试更方便。

代价：不符合"输入寄存器只读"的严格语义。对演练用途可以接受。

### 决策 2：寄存器值固定初值，不自动漂移

上电时温度 = 253（25.3℃）、湿度 = 605（60.5%RH），此后不变，除非主机写入。

理由：联调时主机的写指令能立刻在读回值上体现，收发两条链路一次验证完。自动漂移会让"数变了"这个现象有两种解释，排障时多一个变量。

### 决策 3：收帧机制完全沿用现有骨架

Modbus RTU 靠 3.5 字符静默划分帧边界，现有的"串口中断收字节 + 定时器空闲超时"正是标准做法，从机同样适用，因此 `Serial.c` / `Timer.c` 的结构保留。

### 决策 4：解析与应答在主循环，不在中断里

中断只负责收字节和判帧尾。0x10 写 123 个寄存器的应答在 9600 波特率下要发 8 字节约 8.3ms，若在中断里同步发送会阻塞所有同级及更低优先级中断。主循环处理则可以随时被打断，不影响收帧。

## 寄存器映射

| 地址 | 名称 | 读写 | 初值 | 说明 |
|---|---|---|---|---|
| 0x0000 | 温度 | R/W | 253 | 单位 0.1℃，253 表示 25.3℃ |
| 0x0001 | 湿度 | R/W | 605 | 单位 0.1%RH |
| 0x0002 | 从机地址 | R/W | 1 | 写入后立即生效 |
| 0x0003~0x003F | 保留 | R/W | 0 | 预留给后续扩展 |

**温度编码**沿用原传感器的约定，以兼容现有 `jiema.c`：

- 非负温度直接存数值：25.3℃ → 253
- 负温度存 `10000 + |T|`：-5.3℃ → 10053

`jiema.c` 中原有的判断 `if (Tem1 < 10000) Tem = Tem1; else Tem = -(Tem1 - 10000);` 正是按这个约定写的，从机保持同样编码即可让主机侧无改动。

从机地址寄存器写入后立即生效。由于 0x06 的应答是原帧回显、0x10 的应答沿用请求中的地址，改地址的那一帧应答仍用旧地址发出，不会自相矛盾。改完后再想访问就必须用新地址。

## 从机状态机

主循环：

```c
if (Serial_GetRxFlag())          // TIM2 判出帧尾，RxLen 为帧长
{
    Modbus_Slave_Process(Serial_RxData, RxLen);
}
```

`Modbus_Slave_Process(uint8_t *frame, uint16_t len)` 的处理顺序：

```
1. 长度检查   len < 4 || len > 256              → 直接返回
2. 地址过滤   frame[0] != 本机地址 && != 0x00    → 静默返回
3. CRC 校验   Modbus_CRC16(frame, len-2) 与末尾两字节比对 → 不通过静默返回
              比对方式：(crc & 0xFF) == frame[len-2] && (crc >> 8) == frame[len-1]
4. 广播判断   frame[0] == 0x00                  → 执行写操作，但不组应答、不发送
5. 功能码分发
   ├─ 0x03 / 0x04  读寄存器
   ├─ 0x06         写单个寄存器
   ├─ 0x10         写多个寄存器
   └─ 其它         → 异常应答，异常码 0x01
```

**第 2、3 步必须静默返回，不能回异常帧。** 这是从机最常见的实现错误：地址不匹配时总线上可能有另一个从机正在应答，本机再发一帧就会撞车；CRC 错误说明帧本身就是坏的（噪声或半个帧），此时应答只会让总线更乱。异常帧**只**在"地址匹配 + CRC 正确，但功能码或数据非法"时才发。

## 异常码

| 码 | 含义 | 触发条件 |
|---|---|---|
| 0x01 | 非法功能码 | 功能码不是 0x03 / 0x04 / 0x06 / 0x10 |
| 0x02 | 非法数据地址 | 起始地址 + 数量 超出 0x0000~0x003F |
| 0x03 | 非法数据值 | 数量为 0 或大于 125；0x10 的字节数与数量不匹配 |

异常帧格式：`[从机地址][功能码 | 0x80][异常码][CRCLo][CRCHi]`，共 5 字节。

## 各功能码的帧格式与实现

### 0x03 / 0x04 读寄存器

请求（8 字节）：`[addr][fc][起始Hi][起始Lo][数量Hi][数量Lo][CRCLo][CRCHi]`

应答（5 + 2N 字节）：`[addr][fc][字节数=2N][数据Hi][数据Lo]...[CRCLo][CRCHi]`

实现要点：

- 数量合法范围 1~125。为 0 或大于 125 → 异常 0x03
- 起始地址 + 数量不得越过寄存器区末尾，否则 → 异常 0x02
- 字节数域是 `2 * N`，不是 `N`

### 0x06 写单个寄存器

请求（8 字节）：`[addr][06][地址Hi][地址Lo][数据Hi][数据Lo][CRCLo][CRCHi]`

应答：**与请求字节完全相同**，直接把收到的请求帧原样发回。

实现要点：地址越界 → 异常 0x02；否则写入并原帧回显。

### 0x10 写多个寄存器

请求（9 + 2N 字节）：`[addr][10][起始Hi][起始Lo][数量Hi][数量Lo][字节数=2N][数据...][CRCLo][CRCHi]`

应答（8 字节）：`[addr][10][起始Hi][起始Lo][数量Hi][数量Lo][CRCLo][CRCHi]`

实现要点：

- **应答中没有数据**，只有 8 字节。这是四个功能码里最容易写错的一个
- 帧长必须等于 `9 + 2N`，且字节数域必须等于 `2N`，否则 → 异常 0x03
- 数量范围 1~123（不是 125，要给帧头留出 9 字节）

## 收发方向切换

```c
ModeO();                                                        // DE=1，驱动使能
Serial_SendArray(TxBuf, TxLen);
while (USART_GetFlagStatus(USART1, USART_FLAG_TC) == RESET);    // 等最后一位移完
ModeI();                                                        // DE=0，回到接收
```

`TC` 不能换成 `TXE`。`TXE` 只表示发送数据寄存器已空，最后一个字节还停在移位寄存器里往外发，此时拉低 DE 会把它截断，从机表现为"偶尔最后一字节丢失、主机老报 CRC 错"。现有主机代码这点是正确的，从机沿用。

## 需要修改的文件

### Hardware/Serial.c / Serial.h

1. **接收缓冲区从 9 字节扩到 256 字节。** 9 字节是按主机应答帧（正好 9 字节）定的；从机要收 0x10 写请求，最长可达 255 字节。现有 `if (RNum < 9)` 的守卫会把超出部分静默丢弃，导致长度对不上、CRC 校验永远失败。F103C8T6 有 20KB RAM，256 字节占 1.25%

2. **新增发送前清理函数。** 进发送模式前执行 `USART_ClearFlag(USART1, USART_FLAG_ORE)` 并读一次 `USART_ReceiveData` 清空。485 收发切换瞬间总线上常有毛刺，不清的话可能在下一次接收时立刻误触发一次 RXNE，把噪声当成帧头

3. **给共享的标量标志加 `volatile`**：`RNum`、`Count`、`TmFlag`、`RxFlag`、`RxLen`。

   `Serial_RxData` 数组本身**不要**加 `volatile`。加了以后 `Modbus_Slave_Process(uint8_t *frame, ...)` 和 `Modbus_CRC16(uint8_t *puchMsg, ...)` 的形参都要跟着改限定符，否则编译器报"丢弃限定符"，改一处就要顺带改一串。数组的竞争问题按"已知限制"第 1 条记录，本期不处理

### Hardware/Timer.c / Timer.h

1. **删除 2 秒轮询标志 `TxFlag`。** 从机不再主动发帧，主循环里判断它的那段一并删除。TIM2 中 `i >= 2000` 的计数器可以删掉

2. **把超时阈值 `Count >= 5` 参数化。** TIM2 是 1ms 中断，5ms 在 9600 波特率下约等于 4.8 个字符时间，满足 Modbus 的 T3.5（3.5 字符 ≈ 3.65ms）。但一旦改用 115200，T3.5 只有 0.3ms，5ms 会让主机先超时。改成 `#define MODBUS_T35_MS` 并在注释里写清换算方法

3. 帧尾判定时的 `RxLen = RNum; RNum = 0; RxFlag = 1;` 顺序保持不变，这个顺序保证了主循环读到的 `RxLen` 和缓冲区是一致的

### Hardware/Modbus.c / Modbus.h

保留现有 `Modbus_CRC16()`，新增：

- `void Modbus_Slave_Init(void)` —— 初始化寄存器区初值
- `void Modbus_Slave_Process(uint8_t *frame, uint16_t len)` —— 主处理入口
- 内部静态函数：`SendException()`、`HandleReadRegs()`、`HandleWriteSingle()`、`HandleWriteMultiple()`
- 发送缓冲 `uint8_t Modbus_TxBuf[256]`

### User/main.c

主循环从"定时发请求"改成"收到整帧就处理"：

```c
while (1)
{
    if (Serial_GetRxFlag())
    {
        Modbus_Slave_Process(Serial_RxData, RxLen);
        OLED_Refresh_Display();        // 见下
    }
}
```

OLED 显示内容改为反映从机状态：

```
Slave:01
Tem:25.3
Hum:60.5
Rx:0000 Err:0000
```

三个计数器的口径要分清，否则排障时会被误导：

- `Rx` —— 收到并处理的**合法帧**数（地址匹配且 CRC 通过）
- `Err` —— 地址匹配但 **CRC 校验失败**的帧数，以及发出的**异常应答**数
- **地址不匹配的帧不计入任何计数器**。RS485 是多点总线，别的从机的应答路过本机是正常现象，计成"错误"只会制造噪声

联调时 `Rx` 一直是 0 说明根本没收到（查接线、A/B 有没有接反）；`Rx` 在涨而 `Err` 不动说明通信健康；`Err` 跟着涨说明波特率/校验位对不上或者线太长受干扰。

### Hardware/jiema.c / jiema.h

从机不再需要解码（温湿度是从机自己产生的，不是收来的）。这两个文件保留在工程里不删除，但主循环不再调用，方便日后恢复主机版本。

## 已知限制与风险

1. **`Serial_RxData` 的共享竞争。** `RxLen` 和缓冲区由中断写、主循环读。主循环拿到帧后到处理完约 1ms，此间若新帧到达会覆盖缓冲区。正常 Modbus 主机发完请求会等应答，不会出现；但若主机超时重发，理论上可能覆盖。本次不处理，仅记录

2. **改从机地址后需用新地址访问。** 写入寄存器 0x0002 后，旧地址不再响应。这是标准行为，但操作者要知道

3. **两块板子需要交叉接线。** A 板 TX → B 板 RX、A 板 RX ← B 板 TX、共地。485 的 A/B 不能接反，接反表现为完全收不到数据

## 验收方式

1. **PC 侧先验：** 用 USB 转 485 模块接从机板，Modbus Poll 或串口助手发
   `01 04 00 00 00 02 <CRC>`，应收到 `01 04 04 00 FD 02 5D <CRC>`（253 = 0x00FD，605 = 0x025D）
2. **写回验：** 发 `01 06 00 00 01 2C <CRC>`（把温度写成 300 = 30.0℃），应答应原帧回显；再发读取指令应读回 0x012C，OLED 应显示 30.0
3. **异常验：** 发一个功能码为 0x05 的帧，应收到 `01 85 01 <CRC>`
4. **双机验：** 另一块板子烧 `3c93c22` 的主机代码，两块对接，主机 OLED 应稳定显示从机寄存器里的温湿度
